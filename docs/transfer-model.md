# 以 Transfer 为中心的操作模型

2026-10-14。本文介绍当前采用的操作模型；详细边界见 [架构文档](../architecture.md)。资金、垫付、偿还、货物转移和阶段盘点均已有实现，盘点已阶段性合并到 `main`，尚未部署。

## Transfer 表达一次变化

一条 Transfer 描述“从哪里，到哪里，多少，什么时候，依据什么”，并保留发起、审批和执行记录。

资金 Transfer 的两端是记账账户，金额按整数分保存；货物 Transfer 的两端是实际或外部库存位置，一条转移可含多个 SKU，各自使用整数数量。两者共用心智模型，数据库里分别保存在 `transfers` 和 `stock_transfers`，不要求合成同一张表。

资金账户、费用和收入是不同性质的记账对象；库存外部位置表达组织边界。箭头表达账务或数量变化，盘盈盘亏等动作不一定发生真实运输。

垫付和盘点的具体业务记录，本质上都是带有特定标记的 Transfer：垫付通过附加垫付记录识别，盘点通过本次专属盈亏端点筛选。申报、确认、偿还、调整和查询等业务逻辑都围绕这些 Transfer 展开，不为同一事实再增添其他独立业务实体或另一套账本。已有垫付标记、偿还匹配，以及薄盘点表只保存必要的附加信息和组织关系；不继续扩展独立报销事件、差异单或调整单体系。

## 资金操作

| 操作 | Transfer 的方向 | 结果 |
| --- | --- | --- |
| 资金期初 | 期初权益 → 社团资金池 | 建立初始资金余额 |
| 收款 | 收入端点 → 组织资金账户 | 组织资金增加 |
| 付款 | 组织资金账户 → 费用等端点 | 组织资金减少 |
| 内部转账 | 组织资金账户 A → 组织资金账户 B | 资金分布改变，合计不变 |
| 成员垫付 | 成员往来账户 → 用户明确选择的去向 | 确认后产生成员欠款；去向决定资金或费用等变化 |
| 偿还垫付 | 组织资金账户 → 成员往来账户 | 资金减少，所匹配垫付的未结减少 |

只有标记为组织资金的账户计入资金合计。成员私人余额不纳入本系统。成员自付采购并记到费用时，组织资金不减少；成员把钱转入组织资金池时，资金池增加。

垫付在普通资金转移上附加 `member_claims` 记录，通过 `transfer_id` 一对一关联，保存成员、申报及确认金额和依据。申报未确认时没有正式分录，确认后才过账。

偿还在付款转移上附加 `repayments` 记录，并用 `repayment_allocations` 保存“还了哪笔垫付、多少”。支持部分偿还和一次偿还多笔；付款只记一次。这些关系参与未结计算，不能仅靠备注替代。

资金正式过账生成平衡分录。受信任用户的普通资金转移自动批准并过账；不受信任用户的普通转移待人工审批。垫付确认与偿还当前仅由受信任用户或管理员办理。

## 货物操作

| 操作 | Transfer 的方向 | 结果 |
| --- | --- | --- |
| 库存期初 | 外部期初端点 → 实际位置 | 建立期初数量 |
| 采购到货 | 外部供应方 → 实际位置 | 组织库存增加 |
| 销售或赠送 | 实际位置 → 外部客户等端点 | 组织库存减少，保留各自动作类型 |
| 内部调拨 | 实际位置 A → 实际位置 B | 来源减少、目标增加，组织总量不变 |
| 丢失或报废 | 实际位置 → 外部损耗端点 | 组织库存减少 |
| 真实退回 | 按实际发生的来源 → 去向新增转移 | 记录新的实物变化 |

外部端点不计入组织库存，也不管理供应方或客户的真实库存。

货物转移按“待审批 → 在途 → 已完成”办理。受信任用户创建时自动批准至在途，所有转移都要额外手动完成；普通用户的完成申请另待审批。批准不扣库存，整笔完成后才生成正式数量流水。

每批独立建一条转移，可含多个 SKU。不设父批次或部分完成。当前位置的保管人由保管关系记录，历史操作人仍保留在原确认和执行记录中。

## 同一个事项的钱和货

采购可以先记垫付、以后记到货，也可以在同一入口一起创建。已有资金记录可直接关联货物转移，无需再次记钱。

同入口创建共享一次数据库事务，失败整体回滚；资金按原规则生效，货物以后手动完成。完成到货不会再次付款，取消货物不会自动退钱，冲销资金也不会自动退货。第一阶段只记金额和数量，不根据采购金额自动估算库存价值。

## 阶段盘点：用专属端点组织调整（已实现）

每次盘点保存名称、说明、创建信息、进行中/已结束状态，以及两个专属盈亏端点 ID。盘点本身不改变余额，也不保存一串 Transfer 编号。

| 类型 | 盘盈 | 盘亏 |
| --- | --- | --- |
| 货物 | 本次盘盈外部位置 → 实际位置 | 实际位置 → 本次盘亏外部位置 |
| 资金 | 本次盘盈收入账户 → 组织资金账户 | 组织资金账户 → 本次盘亏费用账户 |

通过“来源是本次盘盈端点”或“去向是本次盘亏端点”查询本次调整。可以从盘点下新建转移，也可以在普通转移入口选择专属端点，数据关系相同。端点只属于一次盘点。资金查询还包含这些记录通过 `reversal_of` 关联的冲销，两类查询不按结束日期截断。

范围、核对时间、账面数、实点数和原因写在说明或原始盘点单中。首版没有结构化清点明细、差异结清流程或历史错账匹配。漏记运费可补记运费并在说明中记录，无需关联到盘点，也不能再为同一差额重复记盘亏。

盘点结束后，其端点在选择器里默认隐藏，仍可按需显示。结束不取消或完成已有转移，也不表示所有差异已经结清；具体调整是否生效继续看各条转移的状态。

## 更正和追溯

资金录错使用关联原记录的冲销，必要时重新登记。已有有效偿还的垫付需要先处理偿还冲销，不能直接覆盖欠款或匹配。真实退款按新业务记录。

货物已完成转移不直接改数量或取消；按实际原因新增退回、损耗或盈亏转移。现有盈亏转移可用 `related_transfer_id` 关联原已完成转移，复杂历史更正仍待明确。

说明和依据用于解释原因；偿还匹配、原单引用等明确关系用于具体业务计算或跳转，不建立包办所有语义的通用关联表。

同一条转移不能重复过账或完成，但两次独立提交会生成两条记录。网络结果不确定时先查记录，独立重复录入由拒绝审批或留痕更正处理。


实际表为 `FundStocktake` / `fund_stocktakes` 与 `StockStocktake` / `stock_stocktakes`。`/api/fund-stocktakes` 和 `/api/stock-stocktakes` 各提供列表（可选状态）、创建、详情 `{stocktake,transfers}`、修改说明与结束接口。active 登录用户可读，可信用户和管理员可写；名称与端点关联固定，无删除、重开或重新绑定。目录附加可空的 `stocktake:{id,name,status}`，仍返回结束端点；已有选中项保留。盘点页复用原列表和编辑器，只预填普通 Transfer 输入。新表沿用 metadata 建表，本轮未初始化日常库；集中检查不代表浏览器或部署验收。
