## 阶段性构想：自由的账户与转移内核（2026-10-14）

### 核心目的与职责边界

内核应允许用户按实际业务创建不同端点，通过来源、去向及金额或数量表达变化。业务复杂，不能提前按开发者设想穷举用途，再把这些组合写成强制规则。资金和货物各自维护账本，共用账户与转移的基本概念，不要求合并为同一张账户表或流水表。

内核负责可验证的账本事实：引用有效、来源与去向不同、金额或数量有效、资金借贷平衡、数量转移守恒、正式写入的一致性，以及同一条转移不能重复记账。不直接修改余额或库存，查询结果从正式流水计算。

身份授权、业务审核与审批、完成确认、审计记录的组织，以及垫付和盘点的具体规则归服务层。服务层应根据已确认的实际需求提出规则，不因理论风险添加新机制。底层保存必要的记录与引用，不能通过直接调用内核绕过服务层授权。

“自由”首先体现在端点用途和转移表达上。审计要能追溯谁做了什么，但审计本身不应成为内核猜测业务、限制用途的依据。

### 两类账户的共同结构

资金账户和货物账户分别存表，基础字段尽量一致。下面是目标字段，具体表名和接口命名在实施方案中落实。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `id` | 字符串主键 | 账户编号 |
| `name` | 字符串 | 账户名称 |
| `kind` | 固定枚举 | 资金为 `public/private/external`；货物为 `internal` 实际保管、`external` 外部 |
| `member_id` | 资金账户可空成员外键；货物账户为返回字段 | 资金联系人或货物当前负责人，货物侧由负责人历史投影 |
| `avatar_url` | 可空字符串 | 头像图片地址 |
| `tags` | JSON 字符串数组 | 自由分类与筛选标签，默认空数组 |
| `active` | 布尔值 | 是否允许用于新业务 |

账户类型创建后不可修改。需要另一种类型时新建账户；名称、联系人、头像、标签和启用状态可以调整。账户类型与成员绑定独立：私账可以不绑定成员，公账或外部账户也可以绑定联系人。绑定不决定账户类型、余额含义、库存归属或操作权限。

资金公账表示社团持有的资金，私账表示社团与个人之间的往来，外部表示外部收支及期初、盈亏等边界端点。系统不管理成员完整的私人资金余额。

资金公账、私账统一按“正式流入减正式流出”计算余额。私账正数表示此人在社团活动中净拿了钱，应交回社团；负数表示替社团垫了钱，社团应偿还；零表示账户净往来结清。账户净余额与逐笔垫付未结不是同一个指标。

例如公账转给小王私账 500 元，私账为 +500；小王私账向外部支付 300 元后为 +200；交回公账 200 元后为零。自行垫付 100 元则私账为 -100，社团偿还后回到零。

货物实际保管账户（internal）计入组织库存，包含成员长期代管；外部账户不计入组织库存。货物账户只维护一个负责人，创建或编辑 member_id 后自动记录起止时间与变更人；负责人历史是唯一来源，不另存联系人字段。负责人变化不改变数量流水和库存。

头像有图片时展示图片；为空或加载失败时，以去掉首尾空格后的账户名第一个字占位。首阶段只保存图片地址，不增加图片上传系统。

### 标签替代预设用途分类

删除账户的 `external_kind`。前端提供预设标签下拉选项，也允许输入自定义标签；两者保存为同一种字符串，不新增标签管理表。保存时去掉首尾空格、空项和重复项。目录与转移入口的账户选择器都应支持按标签过滤。

标签用于分类、查找和筛选，不参与余额、库存和权限计算，也不作为转移的强制准入条件。修改“供应商”“客户”“印刷”等标签不会改变账本规则。

2026-10-26 用户确认活动收支采用轻量分类方式：通过账户名称、转移说明识别和查找事项，以转移记录已有的 `tags` 归集同一活动，例如“2026秋季展会”。资金和货物记录均可使用同一活动标签，保留自由输入及多标签能力，不新增独立活动模块或强制活动关联。现有标签录入与筛选已实现；后续活动汇总沿用这些标签，汇总功能尚未实现。汇总应区分原始收支、报销或代收交回等内部往来，避免把同一事项重复计入收支；标签本身不改变资金和库存事实。

取消当前货物用途与端点用途的匹配表，不再强制要求到货来源带供应商类型、销售去向带客户类型、退回匹配某种端点用途等。固定 `action_kind` 也不应继续承担用途准入职责；本轮删除固定动作字段，资金与货物转移都以预设及自定义标签表达用途。

### Transfer 的说明与关联

每条转移保留一个可选的文字说明 `description`，不再在创建和完成时分别强制填写两份依据。实际完成时间、操作人、审批及执行事实继续结构化记录；无需为了完成操作重复填写说明。

2026-10-26 已列入下一步开发待办：使用统一图片文件夹集中存放附件，让每条资金或货物转移记录能够关联零张或多张图片，用于保存票据、付款截图及货物凭据。附件关联到转移记录，不改变其金额、数量或过账状态。当前尚未实现；沿用私有存储方向，具体上传、访问权限、关联数据及接口方案在实施前确认。

原单关联用于追溯，不限制原单必须完成、不限制只有盈亏可关联，也不要求两条记录的地点和 SKU 相同。保留引用存在、不能关联自身等基础有效性检查。当前 `related_transfer_id` 可先作为这一单条追溯引用，不因此扩展通用关系表、多种关系类型或独立业务事件体系。偿还匹配等参与业务计算的关系仍单独审查，不能直接当作普通追溯引用放宽。

账户和 SKU 停用只阻止新建转移，已有单据仍可按原流程审批和完成。拒绝、取消保留原因。SKU 已使用后不改变单位，避免历史数量被重新解释。

当前出库库存不足时阻止完成、货物外部到外部禁止转移的规则暂时保留，不将其推导成用途限制。这些属于现阶段服务与业务边界，不能扩展为内核对业务用途的预设匹配表。现有审批和整笔完成流程也暂时保留，其规则由服务层维护。

### 已确认：用普通 Transfer 与金额匹配办理报销

日常流程以“成员先自行支出，过一段时间从公账集中报销”为主，现阶段没有备用金管理需求。私账尽量保持平账是管理目标，不是阻止录入的内核约束：支出批准后暂时为负，付款结算后回到零。

2026-10-26 用户明确日常管理原则：尽可能让成员私账余额保持为零，出现非零余额就尽快核对并办理报销、代收交回或必要的留痕更正。在及时清理成员往来的前提下，日常可用资金沿用公账余额口径，不另算扣减私账后的“可用余额”。存在非零私账时，公账展示仍是当前账面资金，负责人应先处理提示中的往来，再据此安排支出；归零原则不自动改变资金事实，也不代表逐笔结算匹配已经完成。

首页醒目列出所有余额非零的资金私账：正数为“成员应交回”，负数为“社团应偿还”，按绝对值展示金额，并分别汇总两个方向。依据账户类型和正式余额筛选，不要求绑定联系人，也不排除已停用但尚未结清的账户；不同账户、不同方向不相互抵扣。归零后移出提醒，处理仍使用现有资金与结算流程，不增加自动付款、自动结算或禁止录入规则。

支出直接登记为“私账 → 外部”的资金 Transfer，保存金额、去向、标签和一个可选说明。申请待审核时不生成正式分录；批准后计入私账余额，并进入可报销范围。受信任用户代录沿用自动批准规则，表示已认可该支出。

在上述业务口径下，Transfer 的批准结果就是报销认可，不另建认可标记。标签只负责筛选和分类，不能自行赋予审核资格。该口径由报销服务解释；内核不需要理解报销，也不据此限制其他普通转移。

报销付款登记为“公账 → 私账”的普通 Transfer，以金额匹配记录说明该付款结清了哪些已批准支出。一次付款可以匹配多笔支出，一笔支出可以分次结清。匹配不生成另一笔分录，也不直接修改账户余额。

例如小王支出印刷费 300 元、快递费 80 元、用品费 120 元，批准后私账为 -500 元。公账付款 400 元，匹配印刷 300、快递 80、用品 20；私账为 -100，用品尚未报销 100。再付款并匹配用品 100 后，账户余额和这三笔支出的未结均为零。

新模型不再保留独立 `MemberClaim`、`Repayment` 和申报/部分确认流程；保留普通 Transfer 及一张金额匹配表。旧代码与接口本轮删除，旧表在显式开发库重建时清理。本方案不再提供申报金额与认可金额两套事实，金额有误按普通审批或留痕更正处理。

匹配归属以具体私账账户为准，不以联系人或成员编号为准。更换联系人不会转移债务；同一联系人关联多个账户时，也不自动混合结算。账户净余额与逐笔未结分别展示，不能仅凭账户为零认定所有指定支出均已匹配。

报销服务检查匹配双方已正式生效、对应同一私账账户、匹配金额为正、不重复、不超过支出剩余未结、匹配合计不超过付款金额。匹配不是自由备注，参与未结计算；这些检查不施加给未使用报销匹配的普通 Transfer。

匹配只在两端记录有效时计入已结金额，相关冲销须同步影响查询结果。移除旧版先冲销偿还的顺序限制。原支出冲销后，付款仍是有效资金事实，其匹配显示为失效、金额显示为未匹配，由用户核对更正；付款冲销则恢复原支出的未结。不级联冲销，不添加恢复机制或独立状态机。

### 已确认：反向代收采用同一结算匹配结构

成员也可能先代收多笔款，再集中交回公账。它与报销方向相反：原收款为“外部 → 私账”，交回为“私账 → 公账”。原收款使私账为正，交回使余额减少；金额匹配用于说明具体交回了哪些收款。

例如小王代收销售款 200 元和 300 元，私账为 +500；交回公账 400 元，可匹配第一笔 200、第二笔 200，第二笔还需交回 100 元。匹配不新增资金流水。

金额匹配统一命名为“结算匹配”，报销和代收交回共用。结构为 `settlement_transfer_id`（结算转移）、`item_transfer_id`（原收支转移）、`amount_minor`（匹配金额，分）；两条转移的方向足以区分报销与代收交回，不重复存用途枚举或成员编号。对相同两条转移保留一条匹配，支持一对多及多对一。

该结构只处理私账支出报销与代收交回，不扩展为任意债务、跨账户抵扣或通用业务关系系统。双方同一私账、方向相对应、有效金额及不超额等条件归结算服务。代收沿用普通转移审批规则，匹配由可信用户办理。支出和代收分别结算，不新增自动净额抵扣。

### 已确认：库存盘点保留薄结构化表

保留一张薄库存盘点表，表达“一次盘点”，记录名称、说明、进行中/已结束状态、创建信息以及两个本次专属外部账户。与现有 `StockStocktake` 对应，随账户命名整理端点字段，不另建独立数量账本。

| 字段 | 含义 |
| --- | --- |
| `id` | 盘点编号 |
| `name` | 盘点名称 |
| `description` | 盘点范围、核对时间、实际情况及原始单据引用等文字说明 |
| `status` | `in_progress` 或 `ended` |
| `gain_account_id` | 本次盘盈专属外部账户 |
| `loss_account_id` | 本次盘亏专属外部账户 |
| `created_by`、`created_at` | 创建人和创建时间 |

创建盘点及结束盘点不改变库存。两个专属账户属于本次盘点，其关联固定；账户名称或标签修改不改变盘点归属。盘盈盘亏仍登记为普通 Transfer，不依赖外部用途枚举，也不根据标签推断归属。

例如仓库账面 100 本、实点 97 本，记录“仓库账户 → 本次盘亏账户：3 本”；这条转移完成后，账面为 97 本。范围、实点结果和原因可以保存在说明或原始盘点单中。

盘点详情查询来源或去向任一端涉及本次两个专属账户的 Transfer，包含反向更正及待审批、拒绝、取消等普通状态，不以结束日期截断。结束只表示整理状态，并让专属账户在选择器中默认隐藏；仍可按需选择、补录或处理已有转移，不宣称差异已全部结清。

本阶段不增加逐 SKU 的账面数快照、实点数、差异数等结构化清点明细，不自动生成差异调整，不增加差异结清流程。需要逐项录入、当时账面快照或自动计算差异时，再按实际需求单独设计。盘点权限、审核、入口预填、结束与审计组织归服务层；内核只处理普通账户和数量转移。

资金盘点沿用已有薄盘点与专属端点模式，账户改为外部分类后不再依赖收入/费用类型。资金反向更正及冲销如何在详情完整展示，随统一查询方案落实；不新增银行对账明细或自动匹配系统。

### 第一阶段业务范围的收敛

按目前确定的概念，第一阶段日常业务已基本被以下几组能力覆盖。覆盖指业务设计能够表达这些事项，不代表代码已按新方案完成或已经验收。

| 能力 | 表达方式 |
| --- | --- |
| 基础目录与人员联系 | 资金/货物账户、SKU、可选成员联系人、头像、标签与筛选 |
| 资金收付及内部转账 | 普通资金 Transfer；公账余额与私账净往来查询 |
| 成员支出报销与代收交回 | 普通收支和结算 Transfer，加结算金额匹配 |
| 到货、销售、赠送、调拨、退回与损耗 | 普通多 SKU 货物 Transfer，额外整笔完成后生成数量流水 |
| 同一事项的钱与货 | 分别记录事实，以明确引用关联；同入口创建沿用同一事务 |
| 期初、盘点及账面调整 | 普通 Transfer，盘点使用薄表和专属账户组织 |
| 审核、更正和追溯 | 服务层审批与审计；资金冲销、货物新增更正转移及原单引用 |

不再为上述每种用途各建业务单据。第一阶段不新增备用金专用流程、独立垫付申报、清点明细、差异单、自动抵扣、库存估值、成本利润核算、订单或通用业务关系体系。

后续工作主要是把新方案落实到现有代码、查询和界面，并确认结算冲销、代收审核等具体业务细节。正式身份接入、附件能力、部署及备份恢复仍属于原第一阶段的配套交付事项，不能因业务模型收敛而视为已完成，也不在本轮文档整理中扩展其范围。
