## 已交付范围

- 单社团、人民币，正式金额按整数分记录。
- 统一资金转移：来源、去向、金额、日期、说明及业务依据；内核不解释采购、垫付或其它经营用途。
- 预览、自动批准、人工审批、正式过账、幂等、冲销及交易追溯。

- 资金端点标签、来源和去向的独立过滤。
- 库存位置目录及保管人、标签；目前没有库存数量流水。

默认记账对象为社团资金池、其它收入、其它费用、期初权益。默认不创建银行和现金账户。资金池只记录组织拥有的金额，与实际经手人或支付渠道无关。“其它收入／费用”是兜底端点，日常可新建更明确的来源和用途。

## 当前工程边界

资金内核位于 `backend/kernel/accounting.py`，只处理精确金额和通用平衡分录。`modules/funds` 构建方案，`application` 编排身份、批准和执行，`infrastructure` 实现数据库查询、事务及锁，HTTP 入口只适配请求。

垫付标记、偿还匹配、货物审批和实际确认将作为外层能力增加，不为它们另造资金或数量账本。

开发阶段通过 SQLAlchemy metadata 直接建表，没有 Alembic 或历史数据升级流程。普通启动保留数据；需要变更开发 Schema 时，显式重建可丢弃的开发数据。正式部署与数据迁移方案留待成熟阶段。

## 启动与重置

安装和配置见 [README](../README.md)。当前服务器已有忽略提交的 `.env`、依赖和独立 PostgreSQL，根目录运行：

```bash
npm run dev
```

Vue 使用 5173 端口，FastAPI 使用 8000，浏览器通过 Vite 的 `/api` 代理调用后端。

重置时先停应用，再执行：

```bash
npm run dev -- --reset-db
npm run dev
```

重置入口仅在 `AUTH_MODE=development` 下执行，清空配置数据库中的 FGAS 应用表并重新初始化。它不自动在每次启动时运行，也不管理 PostgreSQL 服务。

## 下一步：垫付与偿还的外层追踪

建议沿用总路线图的下一增量，不再重做资金内核：

1. 建立业务成员资料，与开发登录账户分开，允许成员没有登录账号。
2. 在同一资金转移模式上增加垫付标记，保存成员、申报与确认金额、依据，以及对应的逐笔待偿还事项。
3. 在偿还转移上增加匹配关系，支持一次偿还多笔垫付和一笔垫付部分偿还；不重复记付款。
4. 提供成员待确认、已确认未结、已偿还及逐笔明细查询，复用现有审批与转移界面。

最小闭环：成员垫付 1,000 元，确认后组织资金池不因成员私人付款而减少；组织再偿还 400 元，资金池减少 400 元，该笔未结金额为 600 元。

实施前只需细化本增量的成员关联、标记与匹配形状，以及默认匹配顺序。资金事实与外层追踪同时提交，内核仍不理解垫付用途。库存数量与交接随后推进；成本估值、Casdoor 和正式迁移不插入这个增量。
