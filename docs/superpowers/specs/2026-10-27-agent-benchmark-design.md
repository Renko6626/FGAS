## 目的与交付

以一个持续经营、多人协作的虚构同人社团，评价 Agent 从连接到完成日常工作的顺滑程度。比较不同客户端、模型、low/high 连接时，使用相同业务事实和任务，不靠临时凑几条记录判断体验。

交付一个本地脚本入口、一份固定业务数据定义、一组可直接交给 Agent 的任务卡、一份仅供评估者使用的答案与核对说明，以及本机使用说明。v1 不建设自动跑模型、自动评分、会话调度或客户端管理平台；本轮完成配置与任务，不自动启动外部模型做完整基准实验。

基准名称 `gensokyo-circle-v1`，故事截止日期固定为 2026-10-27，社员、商家、展会和交易均虚构，商品题材采用东方Project角色。主要考察正确记账、库存状态、结算、权限、补问及交接。

## 方案及已确认选择

1. 独立 PostgreSQL 基准库和可重复加载脚本：避免污染开发数据，便于重置和横向比较；需要一个本地脚本。用户已选择此方案。
2. 只写情景和任务文档：容易准备，但每轮手工搭数据会漂移。
3. 当前开发库追加情景：页面使用方便，但会混入开发状态，无法独立重置。

用户补充要求脚本模拟业务入口。具体采用现有人工 HTTP `/api` 加载历史，正式受测 Agent 使用原生 MCP `/mcp`。不用初始化阶段的 high 能力代替受测 Agent 办任务，不直接插入或修改流水、正式分录、StockMove、匹配或审计表。

## 脚本职责与运行边界

沿用现有Python、PostgreSQL、Alembic、FastAPI、HTTP客户端和前端依赖；保持分层和部署方式。用户另行确认增加SKU代号和标签，并以新基线替换原SKU接口，不做迁移或兼容。

### 商品契约

- 保留内部UUID关联；新增必填唯一 `code`，如 `ARC-01-A`，去首尾空格并转大写，字母/数字/连字符。创建和编辑均检查重号，重复返回409，不自动改号或复用旧商品。
- 商品仅一个完整`name`，如“博丽灵梦立牌 10cm 春服A款”；删除独立`specification`，不引入SPU或规格层级。
- 简单`tags`数组表达`类别:立牌`、`角色:博丽灵梦`，多角色同人本可带多个角色标签，不建分类/角色表。
- 目录HTTP/MCP支持`code`精确查询、`q`搜索代号或名称、`tag`筛选；编辑以code定位。
- 公开货物明细为`{sku_code,quantity}`，库存、转移、数量流水按`sku_code`筛选；应用层解析内部关联，不保留UUID输入兼容。输出提供sku_code与完整名称，内部sku_id可保留给程序关联。
- 目录页面维护代号、完整名称、单位、标签、图片及启停；选货与库存展示使用代号和名称，不用UUID兜底文案。
- 同步0001，不新增revision/回填；只重建fgas_test和新建基准库，不改日常fgas库。

- 数据库固定为 `fgas_benchmark`，与日常 `fgas`、自动化测试 `fgas_test` 分开；脚本核对实际数据库名，拒绝其他名称。
- 本机连接参数沿用现有开发环境，脚本明确改用基准库名，不打印密码。建库属于本地准备，schema 只通过 Alembic upgrade 建立。
- 初始化复用当前 development 种子和三档登录用户，不新增用户管理接口、不接真实 Casdoor。已有种子账户可通过 HTTP 改名并纳入情景。
- 加载脚本启动自己控制的本地 API 子进程，环境明确指向基准库；使用普通 HTTP 登录和请求创建业务，不向任意现有服务盲目灌入数据。临时进程用完退出，不中断原开发服务。
- 历史目录和交易从 HTTP 入口建立，普通用户提出的申请由管理员通过 HTTP 审批；货物必须经过在途和完成流程才有正式数量。
- 基准连接也通过本人 Cookie 会话签发，提供普通用户 low、受信任用户 low、管理员 low、管理员 high 四种角色组合。受测 Agent 每次只得到当前连接，不能同时得到 high 密钥或 Cookie。
- 已有非空基准库默认拒绝再次灌入。显式 reset 先备份该基准库，再重建、迁移和加载；失败停止，不做自动重试、断点续载或请求恢复。存在连接阻止重建时提示停止基准服务，不自动强杀连接。
- reset 只在用户启动的基准环境执行。业务数据核对是正常只读查询；pytest 仍只允许使用 `fgas_test`，不把原测试脚本或其清表 fixture 指向基准库。
- 提供独立启动命令，API 使用其他回环端口；需要网页时用现有 Vite 的 `VITE_API_PROXY_TARGET` 指向基准 API，前端另用一个端口，不修改代理实现。
- 密钥、数据库备份、UUID 映射及本轮结果保存在已忽略的 `.runtime/benchmarks/gensokyo-circle-v1/` 下；包含密钥的本机文件限制为当前用户读写，不进入提交。提交的配置只含虚构业务事实及符号引用。

建议命令形状为 `scripts/benchmark.py init`、`reset`、`serve`、`check`；命名及进程实现细节交由实施者确定。init/reset 加载后进行一次只读核对，check 复用同一组关键核对项，不形成另一套测试框架。

## 时间、重现与任务隔离

业务日期固定在 2026 年 5—10 月；`created_at`、`posted_at` 和负责人历史时间由真实业务入口在加载时产生，不回写成虚构的过去时刻。

因此这是一套集中补录的历史业务基线，不能声称它覆盖了“已在系统运行半年”的实际入账时间分布，也不能用它证明默认最近 30 天过滤能找到半年以前创建的记录。任务明确按业务日期复盘展会时，可以使用 `basis=effective_date`；一般余额、库存查询继续使用默认实际入账口径。需要进一步覆盖真实过去入账时间时，作为以后独立扩展，不在本次引入时间注入机制。

固定的是业务内容、业务日期、引用关系、状态和应有金额/数量。UUID、密钥、会话及实际加载时间无需跨轮相同。脚本保存本轮符号名到 UUID 的映射，评估者用映射核对，不将数据库主键硬编码到用户任务。

每个写任务从干净基线独立执行；对比 low/high 时也分别恢复基线。明确标注的协作任务才允许前后接力，不能把前一任务留下的数据当成独立任务的起点。新会话只收到站点、本人密钥及任务文本，不收到加载脚本、配置、答案或 UUID 映射。评估说明要求受测 Agent 使用原生 MCP；人工 HTTP 和数据库权限仅归准备/评估者。

## low 的正确回退

“完成”可以是提交待审，也可以是准确整理并交接，取决于原任务的明确授权和当前能力。

1. 能查询的先查询。不能直接审批，不妨碍核对原单和资料。
2. 支持 propose 且用户已授权送审的，提交待审并报告 ID、当前状态及后续人工动作；不能把请求“直接办结”默默降格为新待审付款，尤其原付款已存在时。
3. 资料维护、结算匹配、冲销、审批等无对应提案入口的，整理对象 ID、事实、原因、金额/数量及所需操作，交给人工或另一个已经获用户授权的 high 会话。不得自动寻找、签发、更换 high 密钥或读取 Cookie。
4. 只有缺关键业务事实才补问；低权限不是缺事实。不要重复询问任务中已经明确的规格、金额、日期和授权。
5. 卡面允许的协作任务可由 low 汇总并由 high 接手；low 阶段和 high 阶段各自评估，不能把后来 high 的成功归功于 low 已执行。

自然回复示例：这笔 320 元付款已存在，其中 120 元还没有匹配。我可以核对原支出，但当前连接不能执行匹配。已整理付款和原支出的编号及分配金额，交给管理员处理；本次没有新增付款。

## 验收与接入体验记录

配置验收先通过 HTTP 读回并核对：目录数量、关键 SKU 的 297 及位置、在途与完成申请状态、三个结算样本、负责人历史和四种连接归属。黄金答案来自已声明业务事实和手工复算，不把系统查询值直接写回答案当作正确性证明。

接入与业务分开记录：冷启动是否成功发现指南及原生工具、需要用户做什么、是否重启；任务是否正确查询/送审/执行/补问/交接、关键状态是否准确。时间、工具次数、错误及重复问询可作体验观察，不设武断调用次数门槛。

每个任务按正确完成、正确待审、正确交接、正确等待补充事实或失败记录，并核对允许写入和实际变化。越权绕过、重复付款、把待审/在途说成已记账、虚构库存/利润和越过明确“只送审”的要求均为实质失败。正常补问不计失败。

脚本可运行的检查集中执行一次；相关已有测试仍只运行在 fgas_test。默认不新增永久 pytest、端到端环境或 CI；本轮不自动点击网页、填表或运行客户端交互流程。实际加载与只读核对的命令、输出及尚未执行的模型任务分别报告，不把“数据已加载”说成“Agent 已通过所有任务”。

## 本轮不做

不恢复专用盘点、不做订单/利润/估值、不改权限或申请种类、不创建防重/恢复状态机，不搭模型执行平台，不修改 VPS、反向代理或生产发布。实现中发现现有入口无法表达必要业务时，先报告具体缺口；不借基准配置擅自扩展业务系统。
