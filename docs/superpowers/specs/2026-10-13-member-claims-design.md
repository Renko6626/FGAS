## 已确认背景

- 用户本次明确：实际垫付主要由受信任用户统一代录。

以下带“建议”的规则为本次拟议方案，尚未获得用户确认。

## 本增量目标

受信任用户能替没有登录账号的成员登记垫付、确认金额、记录实际偿还，并查询逐笔剩余欠款。资金分录与垫付明细始终可以核对。

验收主例：资金期初 2,000 元；成员申报并确认垫付 1,000 元，组织资金仍为 2,000 元、成员应付款为 1,000 元；偿还 400 元后组织资金为 1,600 元、成员应付款与该笔未结均为 600 元。费用在垫付确认时记一次，偿还不再重复记费用。

## 可选方案与推荐

### 成员与记账对象

方案 A（推荐）：建立独立成员资料，每个成员关联一个受管理的应付科目；成员可以没有登录账号。本增量不建立成员自助申报及登录绑定。逐笔垫付负责解释应付款余额。

方案 B：所有成员共用一个应付科目，在每条分录增加成员维度。成员较多时科目更少，但需要扩展现有分录、查询和校验，当前增量收益不足。

采用 A 可继续使用现有两端点资金转移和通用平衡分录。业务成员姓名与实际录入、确认人的登录身份分开保存。同名成员按稳定编号区分；改名不改变记录归属。

### 录入与确认

建议本增量垫付和偿还写操作仅开放管理员与受信任用户，普通用户保留现有普通资金申请权限及已登录查询范围。登录账号与成员之间暂不建立归属关系。

代录垫付时可“保存待确认”，也可在依据齐全时“确认并记账”。受信任用户可以确认自己代录的记录，不增加必须由第二人审批的规则。确认不是新的权限等级，沿用受信任用户业务权限。

待确认不生成正式分录；确认金额可小于申报金额，必须记录差额原因，不能大于申报金额。零认可通过拒绝处理。待确认记录不做自由编辑，错误可拒绝后重新录入；保留原记录及理由。

确认后的金额不可覆盖；改错走冲销后重新录入。待确认、拒绝和正式确认的状态与对应资金转移保持一致，不建立可独立变化的第二套审批状态。

### 偿还与匹配

建议记录实际已付款事实：选择成员、付款资金账户、金额、实际付款日期和依据，先预览，再确认入账。该确认不会自动发起银行付款。

默认仅匹配该成员已经正式确认且尚未结清的垫付，按服务器记录的确认时间、再按稳定编号排序。允许在提交前手动调整分配，一次付款只对应一个成员，可以匹配多笔垫付。

每笔分配为正数，匹配合计必须等于付款金额，不能跨成员、重复匹配同一笔或超过当前未结。超额付款拒绝，不自动形成备用金、借款或负垫付。备用金、代收款及不同往来抵销建议本阶段均不做。

预览展示匹配结果及所依据版本，提交携带并保存这个结果。提交时在现有串行锁内重查未结；版本或可偿还金额变化时拒绝并要求重新预览，不能悄悄改配其他垫付。实际采用的分配和系统默认／人工调整依据保留在历史记录中。

## 数据与记账方向（待确认）

只在外层增加以下持久化对象，不增加新账本或可编辑余额：

| 对象 | 关键内容与约束 |
| --- | --- |
| Member | 稳定编号、姓名、备注、唯一应付科目引用；不含角色或登录凭据 |
| MemberClaim | 成员、唯一资金转移引用、原始申报金额、正式确认金额、依据、差额原因、确认时间；状态和版本以关联转移为权威 |
| Repayment | 成员、唯一付款转移引用、付款依据、匹配方式 |
| RepaymentAllocation | 偿还、垫付及分配金额；同一偿还内每笔垫付最多出现一次 |

金额均存整数分。已偿还和剩余金额从有效正式记录计算，不保存可任意修改的剩余欠款。

- 垫付确认：成员应付科目 → 用户明确选择的费用科目。建议首版只接受费用类去向，兜底为现有“其它费用”；不自动确认为库存价值，也不根据说明选科目。
- 偿还：组织资金账户 → 该成员应付科目。只产生一笔实际付款转移。
- 成员应付科目为非资金负债科目，不参与资金池合计。创建成员时一并创建该科目并建立唯一关联。
- 系统创建的成员应付科目必须通过垫付／偿还业务入口使用；普通转移入口、普通账户修改入口不能绕过附加校验。组织已有普通科目保持原有语义。
- 首版不提供导入历史未结垫付的专门期初入口；正式初始化的成员欠款按总路线图后续落实，不将其伪记成本期费用。

原始提交内容与正式确认内容分开保留：原始申报请求快照用于提交重试去重；确认保存金额、原因及内容版本。调整确认金额不能改写原始申报快照，重复旧提交不能恢复旧金额。确认以期望版本校验；重复确认不得再次记账。

## 事务、审批与更正

成员标记、匹配、资金分录、状态与审计在同一数据库事务内完成。继续使用现有 PostgreSQL 事务咨询锁，不引入异步过账或新锁基础设施。

建议扩展现有应用层资金入口，按关联业务记录执行垫付／偿还校验，底层金额与分录内核保持通用。普通批准或冲销请求遇到关联业务时必须执行同样规则或明确拒绝；不得只修改分录。

- 原始申报提交、偿还提交和冲销复用“实际操作者 + 幂等键”的去重范围；相同键不同完整业务内容返回冲突。
- 确认绑定当前版本和本次确认内容，在锁内完成；首次成功后同一版本再次请求返回状态冲突，用户可查询当前结果。
- 未偿还垫付可整笔冲销，资金分录与有效债务同时取消；已偿还垫付先冲销其相关偿还，再冲销垫付。
- 偿还可整笔冲销，在同一事务中恢复资金和涉及垫付的未结金额；原匹配记录保留并由冲销关系判断失效。
- 本增量垫付、偿还所产生的冲销记录不可再次冲销；冲销操作本身有误时重新登记业务。应沿 `reversal_of` 识别关联业务，不能仅检查当前转移是否直接带有业务标记。普通资金原有更正行为不在此增量扩改。
- 有尚未完成的冲销时阻止对相关垫付继续偿还。涉及本增量记录的冲销同样只允许管理员和受信任用户办理；普通资金原有权限不变。
- 同时偿还同一笔时串行重查，不能重复清偿；返回明确冲突，保留用户输入以便重新预览。
- 暂不直接修改正式匹配，不做级联自动冲销、净额抵销或复杂历史重算。

## 模块与接口方向（待确认）

沿用 `kernel → modules → application → entrypoints` 的职责划分及 infrastructure 持久化适配方式，不建立通用插件或工作流引擎。

- `backend/modules/member_claims/`：本增量实际使用的金额确认、可偿还校验和分配规则，不操作数据库事务。
- `backend/application/member_claims.py`：成员资料和查询、垫付及偿还编排；复用资金应用层的过账能力。
- `backend/application/funds.py`：统一资金批准和冲销入口执行关联业务校验；通过共用的低层业务规则避免应用服务相互循环调用。
- `backend/infrastructure/models.py` / `store.py`：新增对象、关联查询及原子写入；现有串行锁和事务边界继续生效。
- HTTP 建议增加 `/api/members`、`/api/member-claims`（含确认／拒绝）、`/api/repayments/preview` 和 `/api/repayments`。记录详情关联现有资金转移；冲销复用现有入口并补齐业务保护。具体请求与响应在获批后的实施计划中固定。
- 前端沿用现有导航、表格及弹窗：新增成员及未结查询入口，包含代录垫付、确认和偿还操作。现有资金流水可进入相关明细；待确认事项可从原审批入口找到，但不能用原普通批准动作跳过确认金额展示。
- 前端展示待确认申报额、正式确认额、有效偿还额与剩余额，拒绝和冲销可追溯。未绑定登录账号不影响代录，成员资料不自动创建开发用户。

## 实施次序与验证边界

确认本设计后，任务级计划按以下依赖组织：成员与受管理科目 → 垫付申报和确认 → 偿还与逐笔匹配 → 查询和前端接入 → 集中回归与阶段文档。冲销及入口绕过保护随所属垫付／偿还任务完成，不留到最后再补。

保留现有四个资金测试，复用实际 PostgreSQL 夹具；新增测试只覆盖本增量真实行为缺口：

1. 主例及部分认可：申报 1,000、确认 800 时保留 200 元差额原因，资金池不变、应付款为 800；另用主例验证确认 1,000、偿还 400 后未结 600。
2. 一次偿还跨两笔垫付、手动分配与超额／跨成员拒绝；默认分配顺序有独立可观察预期。
3. 普通资金接口不能绕过受管理科目约束；角色或版本变化不能继续过账。
4. 重试、竞争偿还及数据库中途失败不会留下重复或部分付款、匹配及审计；选择最合适层验证，不在多层复制。
5. 偿还冲销恢复未结；有有效偿还的垫付冲销被拒绝。

具体用例可合并，数量不作为验收指标。不为成员 CRUD、文案及布局单独增加永久测试。前端运行 `npm run build`，必要时截图；不自动点击、填写表单或做浏览器交互测试。

`tools/run_tests.sh` 目前只跑 `backend/tests/test_funds.py`，实施时随新增用例调整入口，确保相关测试纳入同一次回归。测试仅使用独立数据库。

沿用开发直接建表路线；优先用新增表表达，不无故破坏现有数据。若最终字段调整必须重建现有开发库，需在执行前说明并取得该次清空数据授权。编写计划不启动服务或清空数据库。

## 用户需确认的推荐方案

1. 首版使用独立成员目录、每成员一个受管理应付科目，暂不绑定登录账号；垫付及偿还由管理员和受信任用户办理。
2. 代录支持待确认和直接确认；可部分认可并记录原因，受信任用户允许确认自己代录的记录。
3. 默认按最早确认顺序偿还，允许手动分配；超额拒绝，备用金和代收款本阶段不做。
4. 首版垫付去向限费用类；冲销遵循先撤销相关偿还、再撤销垫付的顺序，关联冲销记录不可再次冲销。
