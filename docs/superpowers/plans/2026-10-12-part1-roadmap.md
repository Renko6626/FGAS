# Part 1 开发路线图

> 执行说明：本文是里程碑级路线图，不是可以直接逐项编码的详细实施计划。开工前确认对应阶段的技术和业务决策，再用 Superpowers writing-plans 细化当前里程碑；执行时按用户选择使用 executing-plans 或 subagent-driven-development，不因本文自动启动实施或委派。

**Goal:** 实现 architecture.md v0.4 Part 1，可靠回答组织资金、成员保管货物、交易历史和审批来源。

**Architecture:** 延续模块化单体与中央权威账本。资金和数量流水通过统一过账提交，业务服务编排实际动作；查询读取正式事实或可重建结果。按完整业务增量推进，每个增量包含必要录入与查询，不先一次建完所有抽象层。

**Tech Stack:** FastAPI + Vue 已确认；TypeScript / Vite / Naive UI、Pydantic、SQLAlchemy 2 / PostgreSQL（当前直接建表，正式迁移后续落实）、私有附件与 Docker Compose 沿用文档方向。认证复用现有 Casdoor SSO，三档权限由本系统管理。当前服务器开发测试，另一台服务器全新正式部署；Casdoor 具体接入配置待落实。

**Spec:** [architecture.md](../../../architecture.md)，v0.4，Part 1。

## 全局约束

- 只实现 Part 1；估值、成本分摊、经营归属、管理分析、POS 自动导入和 Agent 接入延期。
- 只管理组织拥有的货，实际位置与历史保管关系分别记录。
- 数量转移是底层事实，Transfer 是共用的外层审批与确认流程；主状态“待审批 → 在途 → 已完成”，受信任用户通常走“在途 → 已完成”；状态变化不扣库存，没有虚拟在途位置。
- 未估值显示为“未估值”，采购付款不能自动当成库存价值或商品成本。
- 正式记录通过更正或冲销纠错，不能覆盖历史或直接改余额。
- 基本权限、审批依据、幂等、事务和审计随第一条正式操作建立；后续按实际业务扩展。
- 技术栈、接口和重要边界实施前确认；此路线图不代替架构决策授权。
- 按用户要求控制验证范围：不机械 TDD，不为每个表或页面新增测试，不穷举 corner case，不搭建大型测试辅助框架。
- UI 默认只做构建和必要截图，不自动点击、填表或执行浏览器交互验收。

## 2. 第一条链：期初资金、收付与账户转账

- [x] 随本增量建立最小项目、开发数据库直接建表、身份入口及实际需要的分层目录。

- [x] 提供分类选择来源、去向和金额的自由录入；可修改预设只预填，正式分录由明确选择的对象及账户语义生成。
- [x] 统一资金转移模式覆盖收付、转账、垫付和偿还；内核不识别垫付业务，逐笔标记与匹配作为外层附加能力在下一增量补齐。
- [x] 账户语义、分录生成与过账校验分开；不做规则编辑器或文本推断科目。
- [x] 建立最小统一过账路径：权限、批准或免人工审批依据、锁内校验、幂等、事务和审计。
- [x] 提供账户余额、交易明细和审批追溯，以及最薄的录入与查看界面。

主要所有权：funds、kernel/accounting、kernel/posting 和应用编排；基础设施提供数据库实现。接口形状在本增量详细计划中确定。

完成标志：记录一笔收款或付款后能追溯余额；账户间转账不改变资金总额；重复请求不重复记账。使用真实数据库确认一次写入失败能整体回滚。

实施状态：第一条资金链原型已交付。Casdoor 在本机原型中由占位账户替代；库存位置仅提供带标签目录。阶段开发与审阅分别采用用户指定的 sol low / sol medium。

## 3. 第二条链：整笔垫付、部分偿还与逐笔匹配

- [x] 确认垫付确认权限、默认匹配顺序及备用金和代收款是否进入首版范围。
- [x] 在已有资金转移上附加 MemberClaim 垫付标记：待确认、正式确认、依据和确认版本；不另建资金记录模式。
- [x] 在已有付款转移上附加偿还标记及 RepaymentAllocation，支持部分偿还及一笔偿还匹配多笔垫付，不重复生成付款。
- [x] 提供成员未结总览、逐笔金额、偿还历史和操作入口。

主要所有权：member_claims 负责外层标记与匹配；资金记录统一复用 funds 和账本内核；应用层组合并验证附加信息，经同一过账入口原子提交。

完成标志（相关真实数据库检查已通过）：费用去向垫付 1,000 元、偿还 400 元后，在没有其他往来时逐笔未结与成员往来账均为 600 元；偿还只产生一次付款事实。成员转入资金池则按实际端点增加资金；普通往来另列，不能以净余额替代逐笔未结。

- [x] 在获准 PostgreSQL 环境执行全部十个数据库用例并通过；UI 交互验收仍未执行。

2026-10-13 实现、逐任务审阅及集中代码审阅完成。用户开放权限后修复 PostgreSQL 查询中的 JSON 去重问题，`./tools/run_tests.sh` 十个用例全部通过，前端构建通过。按用户授权创建公开仓库并通过 PR 交付；未部署、截图或执行浏览器交互。

暂不建设完整借款系统或自动抵销其他往来。

## 4. 第三条链：库存期初、到货与出库

- [ ] 建立 SKU、实际位置、保管关系和正式数量流水。
- [ ] 建立共同数量转移能力，支持库存期初、采购到货、销售、赠送、丢失和实际退回，不为每类场景重复实现库存内核。
- [ ] 同时接入最薄的外层审批与确认：受信任用户自动批准，不受信任用户先人工审批；均进入在途，再额外手动整笔确认完成，每条可含多个 SKU，每批独立 Transfer。
- [ ] 保留商家和客户等外部边界、损耗去向、原始依据及不同动作类型。
- [ ] 查询每个人保管的货及数量历史；到货和收付款可以同入口提交，也可以后续关联，不能重复记录已有事实。

主要所有权：warehouse、kernel/stock；资金与货物同动作需要正式提交时，由应用层组合并原子过账。

完成标志：100 本到达 A 后可查到 A 的数量和到货依据；到货不改变资金余额，关联已有垫付不重复计债；并显示库存尚未估值。

暂不建立成本批次和估值表。SKU 数量已确认统一为整数计数，不支持小数精度配置；负库存边界按已确认的整笔执行校验落实。

## 5. 第四条链：关联盘点盈亏与差异处理

> 2026-10-13 用户确认简化：每批独立 Transfer，不再实施分批执行、分别交出/接收或未收妥余额。收货差异另建盘点盈亏记录；本节与第 4 节紧密相连，实施计划应把最小差异入口纳入同一库存阶段，完整盘点体验再随试用补齐。

- [ ] 落实收货核对依据、差异归属位置及审批；不因少收自动认定组织损失。
- [ ] 在整笔 Transfer 上关联实际核对和独立盘点差异记录，调整复用数量转移内核及批准、在途、手动确认流程。
- [ ] 盘盈从外部盘盈边界进入实际位置，盘亏从实际位置流向外部盘亏边界；边界不计组织库存。
- [ ] 显示账面数量、已知未调整差异、原转移、差异依据和调整历史；转移完成不等于差异已处理。
- [ ] 区分货物确实丢失、少发仍在来源位置及原始登记错误；真实退回另建 Transfer，有依据更正不覆盖正式记录。

主要所有权：warehouse 保存转移和差异调整；reconciliation 保存比较依据，按实际实现需要落地，不搭空模块；应用层组织审批及统一提交，数量约束复用库存内核。

完成标志：A 原有 100 本，批准 A→B 30 本不扣货；手动完成后账面 A 70、B 30，记录 B 实收 28 及差异 2；核实实际损失并确认关联盘亏后 A 70、B 28，组织总量 98。若实际少发且 2 本仍在 A，有依据更正或关联 A 盘盈 2、B 盘亏 2 后，A 72、B 28，组织总量保持 100。

验证重复确认、重复差异调整与同一份库存的竞争执行，采用代表性场景，不扩展到大规模压力或所有并发组合。两批各建一条 Transfer，各自完成，无父单和分批执行层。

完成标志：差异不会自动记成收入、费用或库存调整；一笔错误可以留痕修正并追溯原记录；普通成员能通过少量入口完成日常登记。

## 验证范围

优先保留以下关键证据，随所属增量落实，不集中到最后：

- 正式资金凭证平衡，账户转账不重复计钱。
- 相同动作重试不产生第二份事实，事务失败不留下部分正式记录。
- 垫付部分偿还后，逐笔未结与往来账一致。
- 内部整笔转移不改变组织总量，获准的盘盈盘亏按依据改变总量；重复完成、重复调整和竞争执行不重复扣增。
- 无权操作和修改已批准内容不能正式提交；实际执行保留身份和批准依据。
- 在空环境完成一次恢复并核对共同样例。

采用简短的真实行为测试和实际数据库核对；复用已有用例，避免在 HTTP、应用层和数据库层机械复制同一场景。常规 CRUD、样式和文案以已有检查、构建或必要截图验证。常用更正随实际需求覆盖，不预先穷举异常矩阵。
