# Part 1 开发路线图

> 执行说明：本文是里程碑级路线图，不是可以直接逐项编码的详细实施计划。开工前确认对应阶段的技术和业务决策，再用 Superpowers writing-plans 细化当前里程碑；执行时按用户选择使用 executing-plans 或 subagent-driven-development，不因本文自动启动实施或委派。

**Goal:** 实现 architecture.md v0.4 Part 1，可靠回答组织资金、成员保管货物、交易历史和审批来源。

**Architecture:** 延续模块化单体与中央权威账本。资金和数量流水通过统一过账提交，业务服务编排实际动作；查询读取正式事实或可重建结果。按完整业务增量推进，每个增量包含必要录入与查询，不先一次建完所有抽象层。

**Tech Stack:** FastAPI + Vue 已确认；TypeScript / Vite / Naive UI、Pydantic、SQLAlchemy 2 / Alembic / PostgreSQL、私有附件与 Docker Compose 沿用文档方向。认证复用现有 Casdoor SSO，三档权限由本系统管理。当前服务器开发测试，另一台服务器全新正式部署；Casdoor 具体接入配置待落实。

**Spec:** [architecture.md](../../../architecture.md)，v0.4，Part 1。

## 全局约束

- 只实现 Part 1；估值、成本分摊、经营归属、管理分析、POS 自动导入和 Agent 接入延期。
- 只管理组织拥有的货，实际位置与历史保管关系分别记录。
- 数量转移是底层事实，Transfer 是共用的外层审批与确认流程；主状态“待审批 → 在途 → 已完成”，受信任用户通常走“在途 → 已完成”；状态变化不扣库存，没有虚拟在途位置。
- 未估值显示为“未估值”，采购付款不能自动当成库存价值或商品成本。
- 正式记录通过更正或冲销纠错，不能覆盖历史或直接改余额。
- 基本权限、审批依据、幂等、事务和审计随第一条正式操作建立；后续按实际业务扩展。
- 技术栈、接口和重要边界实施前确认；此路线图不代替架构决策授权。
- 按用户要求控制验证范围：不机械 TDD，不为每个表或页面新增测试，不穷举 corner case，不搭建大型测试辅助框架。
- UI 默认只做构建和必要截图，不自动点击、填表或执行浏览器交互验收。

## 1. 开工前：确认影响第一条业务链的决定

- [x] 确认主框架 FastAPI + Vue，配套沿用文档方向。
- [x] 身份认证复用现有 Casdoor SSO，不另建身份平台。
- [x] 当前服务器仅开发测试；验证后在另一台服务器从空数据库开始，不迁移测试账目。
- [x] 首个管理员由部署配置指定，后续权限在本系统管理。
- [ ] 落实 Casdoor 的具体接入方式及各环境配置。
- [x] 单实例管理单社团，仅人民币；其他社团部署独立实例，不建设多组织和多币种。
- [x] 沿用文档的资金复式记录与货物转移流水原则，不另设计记账口径。
- [x] 普通记账明确选择来源与去向；描述预设可以修改，不依据描述自动映射全部科目。
- [ ] 在资金链实施设计中落实精度、可选对象及垫付等明确场景的确定性规则。
- [x] 权限固定三档：管理员、受信任用户、不受信任用户；受信任用户普通业务自动批准，不受信任用户业务写操作人工审批。
- [x] 受信任用户或管理员可审批不受信任用户的普通业务申请，审批不能越过自身业务权限。
- [x] 管理员专属敏感操作为权限与访问启停、关键记账规则或科目配置修改，以及备份恢复或正式数据替换。
- [x] Casdoor 负责登录认证，本系统管理员管理三档权限，不从 Casdoor 自动映射。
- [ ] 准备一套小型样例：组织资金 2,000 元，成员垫付 1,000 元，100 本到货，偿还 400 元，交出 30 本、接收 28 本、退回 2 本。

其余决策在相应里程碑开始前确认，不要求此时回答全部后续问题。不先确定成本批次、经营标签或未来分析模型。

交付：一页已确认决策和样例，足以启动资金链。

## 2. 第一条链：期初资金、收付与账户转账

- [x] 随本增量建立最小项目、数据库迁移、身份入口及实际需要的分层目录。
- [x] 建立资金账户、科目、凭证和分录，实现期初、收款、付款及内部转账。
- [x] 提供分类选择来源、去向和金额的自由录入；可修改预设只预填，正式分录由明确选择的对象及账户语义生成。
- [x] 统一资金转移模式覆盖收付、转账、垫付和偿还；内核不识别垫付业务，逐笔标记与匹配作为外层附加能力在下一增量补齐。
- [x] 账户语义、分录生成与过账校验分开；不做规则编辑器或文本推断科目。
- [x] 建立最小统一过账路径：权限、批准或免人工审批依据、锁内校验、幂等、事务和审计。
- [x] 提供账户余额、交易明细和审批追溯，以及最薄的录入与查看界面。

主要所有权：funds、kernel/accounting、kernel/posting 和应用编排；基础设施提供数据库实现。接口形状在本增量详细计划中确定。

完成标志：记录一笔收款或付款后能追溯余额；账户间转账不改变资金总额；重复请求不重复记账。使用真实数据库确认一次写入失败能整体回滚。

实施状态：第一条资金链原型已交付。Casdoor 在本机原型中由占位账户替代；库存位置仅提供带标签目录。阶段开发与审阅分别采用用户指定的 sol low / sol medium。

## 3. 第二条链：整笔垫付、部分偿还与逐笔匹配

- [ ] 确认垫付确认权限、默认匹配顺序及备用金和代收款是否进入首版范围。
- [ ] 在已有资金转移上附加 MemberClaim 垫付标记：待确认、正式确认、依据和确认版本；不另建资金记录模式。
- [ ] 在已有付款转移上附加偿还标记及 RepaymentAllocation，支持部分偿还及一笔偿还匹配多笔垫付，不重复生成付款。
- [ ] 提供成员未结总览、逐笔金额、偿还历史和操作入口。

主要所有权：member_claims 负责外层标记与匹配；资金记录统一复用 funds 和账本内核；应用层组合并验证附加信息，经同一过账入口原子提交。

完成标志：垫付 1,000 元、偿还 400 元后，逐笔未结与成员往来账均为 600 元；偿还只产生一次付款事实。

暂不建设完整借款系统或自动抵销其他往来。

## 4. 第三条链：库存期初、到货与出库

- [ ] 建立 SKU、实际位置、保管关系和正式数量流水。
- [ ] 建立共同数量转移能力，支持库存期初、采购到货、销售、赠送、丢失和实际退回，不为每类场景重复实现库存内核。
- [ ] 同时接入最薄的外层审批与确认：受信任用户自动批准后确认实际完成，不受信任用户先人工审批；直接完成可一次提交。
- [ ] 保留商家和客户等外部边界、损耗去向、原始依据及不同动作类型。
- [ ] 查询每个人保管的货及数量历史；到货和收付款可以同入口提交，也可以后续关联，不能重复记录已有事实。

主要所有权：warehouse、kernel/stock；资金与货物同动作需要正式提交时，由应用层组合并原子过账。

完成标志：100 本到达 A 后可查到 A 的数量和到货依据；到货不改变资金余额，关联已有垫付不重复计债；并显示库存尚未估值。

暂不建立成本批次和估值表。数量精度、负库存边界在本增量实施前确认。

## 5. 第四条链：完善外层确认、分批交接和差异结清

- [ ] 确认不预留库存的首版建议、分批交接、退回及损耗结清规则。
- [ ] 扩展上一增量的 Transfer 外层流程，完善明细、分批交出和接收记录；沿用三种主状态，不建立另一套调拨记账逻辑。
- [ ] 实现实际交出、接收、退回和在途损耗，按正式流水计算未收妥数量。
- [ ] 提供来源、目标、计划进度、实际数量和未完成调拨查询。

主要所有权：warehouse；审批复用已有应用流程；数量约束复用库存内核。

完成标志：批准不扣货；交出 30 本、收到 28 本后剩余 2 本未收妥；实际退回 2 本后 A 有 72 本、B 有 28 本，组织总量仍为 100 本。

验证重复确认与同一份库存的竞争执行，采用代表性场景，不扩展到大规模压力或所有并发组合。

## 6. 试用补齐：盘点、对账、更正与基础操作体验

- [ ] 实现盘点和资金对账：记录比较时点、账面值、外部或实点值、差异及处理依据。
- [ ] 随前述链路的试用需求补齐更正或冲销；这一阶段完成相关页面和最常用更正场景。
- [ ] 汇总审批待办、交易追溯、附件访问与基本手机布局。
- [ ] 确认历史补录、更正受后续偿还或交接影响时的处理边界。

主要所有权：reconciliation 保存比较依据；资金和库存模块生成正式调整；应用层组织审批及更正。

完成标志：差异不会自动记成收入、费用或库存调整；一笔错误可以留痕修正并追溯原记录；普通成员能通过少量入口完成日常登记。

早期没有支持的复杂更正应明确拒绝并提示处理方式，不能允许直接改账绕过约束。

## 7. 正式使用前：初始化、恢复与一次综合核对

- [ ] 开发环境使用测试样例；正式服务器空库初始化后，另行录入真实期初：资金、各位置数量、逐成员未结垫付及需要接续的未收妥货物。
- [ ] 实现数据库、附件和版本清单的基本备份包，确认恢复一致性及权限。
- [ ] 使用测试备份在空环境恢复一次，核对资金、数量、未结垫付、交接、审批和附件；不将该测试备份作为正式服务器的初始数据。
- [ ] 使用共同样例综合核对四个核心问题，完成基本运行与恢复说明。

完成标志：测试演练证明可以恢复并继续查询和记账；正式服务器能用相同代码及独立配置从空库启动，按部署配置建立管理员并开始记录真实业务。上线不依赖迁移开发测试账目。

自动备份、异地副本和长期归档在明确使用需求后完善，但基本可恢复能力是正式使用的前提。

## 验证范围

优先保留以下关键证据，随所属增量落实，不集中到最后：

- 正式资金凭证平衡，账户转账不重复计钱。
- 相同动作重试不产生第二份事实，事务失败不留下部分正式记录。
- 垫付部分偿还后，逐笔未结与往来账一致。
- 交出、接收及差异结清后数量守恒；重复和竞争执行不重复扣增。
- 无权操作和修改已批准内容不能正式提交；实际执行保留身份和批准依据。
- 在空环境完成一次恢复并核对共同样例。

采用简短的真实行为测试和实际数据库核对；复用已有用例，避免在 HTTP、应用层和数据库层机械复制同一场景。常规 CRUD、样式和文案以已有检查、构建或必要截图验证。常用更正随实际需求覆盖，不预先穷举异常矩阵。
