# Agent 接入实测总结与下一步计划

状态：本文件保留实施前原始实测、建议和待确认问题；用户已于2026-10-27确认 me、自动业务编号、在途查询及公开 code 一次切换，随后确认直接同步现有 0001 基线，不新增 revision，不迁移或回填旧库，日常 fgas 不改。本文下方“建议”“待确认”“本次交付仅为计划”等句子只记录当时状态，不代表现在仍未实施。前四批功能已经完成并通过软件检查；定向真实模型复测结果见 [后续证据](../../ai/2026-10-27-agent-access-followup.md)，实施和逐任务证据见 [实施计划](2026-10-27-agent-access-implementation.md)。

建议分四批推进：先补me、并列交接及业务边界说明；再统一业务编号和网页定位；随后明确在途计划查询；最后定向复测。利润问题先处理能力与数据范围，在途问题同时处理字段与统计定义，两者分别验收。

**Goal:** 让 Agent 能确认当前身份，用可读业务标识查询和操作，在权限不足时提供人工与 high Agent 两条并列路径，并减少利润、库存和在途口径误读。

**Architecture:** 沿用现有模块化单体及四个 MCP 工具。人工 HTTP 使用 Cookie，MCP 使用 Bearer；应用服务统一解释业务标识、授权与查询口径，数据库 UUID 留在内部关联。前端和 MCP 使用一致的业务字段与含义。

**Tech Stack:** 现有 Python / FastAPI / SQLAlchemy / PostgreSQL、Vue / TypeScript / Naive UI，不为本计划新增框架或外部服务。

**依据:** [架构](../../../architecture.md)、[基准设计](../specs/2026-10-27-agent-benchmark-design.md)、[基准包](../../../benchmarks/gensokyo-circle-v1/README.md)。本机实测原始报告位于 `.runtime/benchmarks/gensokyo-circle-v1/runs/luna-high/report.txt`，属于忽略提交的私有运行证据；关键结论在下文独立记录。

## 1. 实测结论与本轮范围

本轮使用 `gpt-5.6-luna`、high 推理强度、Codex CLI 0.160.0，在提交 `9514e1f` 上执行24张卡、26个权限场景，实际28轮模型调用：21项通过、3项部分符合、2项失败。所有钱货及目录写入均符合任务允许范围；答案和引导仍有问题。此结果是一轮本机样本，不作为跨模型成功率或生产验收。

| 实测表现 | 结论 | 后续处理 |
| --- | --- | --- |
| C01自主找指南、配置MCP，重开一次会话后查对余额和正式库存 | 冷接入路径可用；未拿到登录姓名 | 补当前身份查询，保留现有正常重载说明 |
| H02抄错UUID，F05将PEND-88当详情ID查询 | 业务仍需搬运内部标识，业务编号与说明引用混淆 | 全链路使用业务标识，支持按用户提供的引用查找 |
| 7次参数校验错误、2次未找到记录、2次权限拒绝 | 提示可以帮助恢复，首次调用仍存在摩擦 | 明确单对象/列表、时间窗口和资源参数边界 |
| F05只建议切换管理员连接 | 未越权，但交接路径不完整 | 人工、已授权high Agent两条并列，不把升权限当作唯一解法 |
| X01 high只追问日期，未充分处理书未到货 | 没有误入库，但事实冲突处理不足 | 先核实整笔实物事实，再考虑由谁办理 |
| X02 low/high均把两笔280元推成利润0元 | 两项实质失败 | 单独处理能力边界、数据范围和资金口径 |
| C01把账户在途130与10相加报成140 | 正式库存正确，附加计划汇总重复 | 调整在途查询定义、字段和汇总，不依赖Agent自行解释重复行 |

工程主线是身份、业务标识、交接引导；利润与在途分别制定口径及验收。保留现有正式流水、冲销、匹配、在途和整笔完成模型，不引入利润模块、部分完成、盘点恢复、请求恢复或自动重试。

## 2. 当前身份：明确“谁在用哪一个连接”

### 2.1 推荐接口

人工端已有 `GET /api/auth/me`，继续使用当前Cookie会话。MCP建议增加现有query下的单对象资源：

```json
{"resource":"me"}
```

返回沿用 `api_version/data` 包装，建议最小内容为：

```json
{
  "user": {"display_name":"林舟", "role":"admin"},
  "connection": {"name":"林舟的 AI", "level":"low"}
}
```

- 当前身份直接来自已解析的 `AgentAccess`，不接用户编号、分页、时间窗口或任意用户查询参数，不返回密钥。
- `user.role`说明所属用户的系统角色；Agent实际办理能力仍受`connection.level`及现有服务授权约束。管理员的low仍不能直接办理。
- 查询不创建Member、私账或首次记账资料，不把登录用户、业务联系人和货物负责人合并。
- 不新增第五个MCP工具或单独的HTTP `/mcp/me` 路由。身份建议有明确query入口；仅塞入help虽少一次查询，但缺少独立的当前身份契约，作为备选而非同时建设两套接口。

### 2.2 前后端及帮助同步

后端涉及`application/agent_queries.py`、`entrypoints/agent_schemas.py`、`agent_catalog.py`及MCP帮助索引；复用当前每次调用重新检查凭据和用户的机制，不增加身份缓存或存储字段。

前端`api/auth.ts`、`useSession.ts`继续读取人工身份；`AgentConnectionsView.vue`清楚展示每条连接的名称和等级。网页管理员身份不能被展示成“所有客户端当前都在用high”，因为网页没有某个客户端当前Bearer的上下文。

公开指南的接入验证顺序调整为：读取核心说明 → `fgas_help()` → `me` → 一次正常只读业务查询 → 向用户报告身份、等级和结果。姓名有真实来源后再报告，不再靠联系人目录或连接等级猜身份。

## 3. UUID退入内部：先冻结业务标识，再统一入口

### 3.1 改造范围与推荐方案

保留数据库主键和外键，不把UUID变成用户或Agent必须抄写的业务参数。商品已使用SKU代号；下一批优先覆盖账户、成员联系人、资金单、货物单和完成申请。

推荐为需要独立定位的对象提供唯一、稳定的业务`code`。以下前缀仅为方案示例，正式格式和维护规则需确认：

| 对象 | 示例 | 用户和Agent如何使用 |
| --- | --- | --- |
| SKU | ARC-01-A | 保留现有SKU入口及完整商品名 |
| 资金账户 | FA-0001 | 名称用于辨认，code用于精确引用 |
| 货物账户 | SA-0001 | 配合名称、负责人区分储藏室和宿舍 |
| 成员联系人 | M-0001 | 同名时结合备注确认，再引用code |
| 资金转移及其冲销单 | FT-000123 | 查询、审批、冲销、结算引用 |
| 货物转移 | ST-000123 | 查询、批准、直接完成、关联原单 |
| 完成申请 | SC-000123 | 批准/拒绝具体完成申请，另列父货物单号 |

审计、分录、货物明细和匹配行通过父单号、SKU及操作信息展示，不为每一张内部表都增加一套编号。会话、令牌、OIDC subject等认证技术标识不纳入业务编号改造。

建议新生成单据使用简单的数据库原生序列形成可读编号，只承诺唯一、稳定，不要求连续无缺号。目录code可由系统分配或人工维护，需在实施前选择；不建设全局编号服务、补号流程或额外分配表。

采用纯名称定位虽然改动较少，但名称可变、同名存在，难以承担正式单据引用；只改前端显示则无法解决Agent调用时复制UUID的问题。因此推荐公开业务契约使用code，名称作为可读说明和搜索条件。

### 3.2 用户提供的引用与系统单号分开

`PO-08`当前是货物`source_reference`，`PEND-88`是资金说明中的标记，不能未经确认就当成唯一系统单号。

- 货物列表提供按`source_reference`精确筛选；不把它当唯一键，可能返回多个候选。
- MCP资金列表补齐与人工HTTP一致的说明搜索`q`，能按PEND-88等用户已知文字找单；货物搜索也覆盖其原始单据引用。
- 搜索返回可读单号、状态、金额/数量、日期和账户，匹配唯一候选后再按系统code办事；多候选时补问，不取第一条凑结果。
- 列表中的用户引用和系统单号使用不同字段和标签，帮助示例不再把二者混写为`identifier`。

### 3.3 HTTP、MCP和前端一起切换

| 当前接口 | 目标契约建议 |
| --- | --- |
| `/api/transfers/{id}`及approve/reject/reverse | 路径使用FT单号，保留原审批和版本校验 |
| `/api/stock-transfers/{id}`及其动作 | 路径使用ST单号；直接complete仍作用于父单 |
| `/api/stock-confirmations/{id}/approve或reject` | 路径使用SC申请号 |
| 账户/成员目录编辑、私账结算概览 | 使用所属目录的code定位 |
| `source_account_id/destination_account_id/member_id` | 公开业务输入改为相应`*_code`，由应用服务解析内部关联 |
| `fund_transfer_ids/related_transfer_id/reversal_of` | 改为可读单号引用，输出同步使用`*_code` |
| 结算`item_transfer_id`及付款identifier | 引用原收支FT单号与付款FT单号 |
| MCP详情`identifier`、执行`data.identifier` | 统一表示所选业务对象的code，不猜UUID或业务说明 |

列表继续用`filters`。单对象查询建议统一到`identifier`，例如结算概览以私账code定位，减少当前`identifier`与`filters.account_id`的记忆差异；`me`无需定位参数。该调整需先冻结具体Schema，不保留多套字段别名作为默认方案。

前端同步`api/accounts.ts`、`funds.ts`、`warehouse.ts`、`members.ts`、`settlements.ts`及依赖的表单、列表、详情和选择器。公开业务DTO、查询、提交、引用和复制按钮都以业务code为准，正常业务响应移除无须外部使用的UUID，不让Agent面对两套可混用的定位字段；关系解析留在服务层，内核及正式流水仍使用原内部关联。

界面以名称为主、业务号辅助辨认；复制单号和链接不暴露UUID。完成申请与父货物单分别标注，避免把SC申请号用于ST详情或直接complete。

### 3.4 人工定位链接

当前前端使用App.vue中的hash导航，已有`#approvals`、`#transfers`、`#settlements`、`#stock`、`#locations`，尚无单据级深链接。先使用真实可用的页级入口；在code契约落地后，建议沿用现有hash增加定位信息，例如：

```text
/#transfers?code=FT-000123
/#stock?code=ST-000123
/#settlements?account_code=FA-0001
```

这些为拟新增链接，不应提前写成已经可用。实现时让`readPageHash`解析页面及定位参数，页面加载后打开对象。链接只导航和展示，不自动执行审批或写入，后端权限照常检查；不为这一步引入新路由框架。

现有同页登录可做保留hash的局部调整；真实Casdoor回调目前返回根路径，不能仅凭hash解析就承诺跨SSO保留原位置。第一步允许用户正常登录后重新打开交接链接。若需要全自动跨SSO返回定位，再单独确认认证返回流程，不把它默认扩为导航恢复功能。

链接基址使用用户实际打开的网页站点。前后端分离开发时，API端口不能直接充当网页地址；下一轮基准输入需明确网页站点及其原生MCP地址。

## 4. 权限不足：人工与high Agent两条并列路径

用户本轮明确要求两条合法路径并列，下一轮指南与验收都以此为准，不要求所有任务优先人工，也不把high视为不合法的办理方式。

| 路径 | 由谁办理 | low Agent需要交付 |
| --- | --- | --- |
| 人工网页办理 | 具备对应网页权限的本人、受信任用户或管理员 | 业务号、当前状态、已核对事实、具体操作和网页入口；普通用户本人不能办理时，可交给有权限的人 |
| high Agent办理 | 用户明确授权、使用合法high连接的Agent；high连接仍要求管理员所属 | 相同业务号及操作清单，注明已完成/未完成部分；由high读取最新状态后继续，沿用原单和已有付款 |

两条路径都遵守原业务授权。low不自行签发或更换凭据；用户选择high时使用已授权会话，或由管理员按现有网页流程配置本人的high。更换连接后按客户端要求刷新工具并重新核对`me`，不重做先前已成功的登记。人工仍用Cookie，Agent仍用Bearer。

双路径用于完成交接，不增加每次记账都问一次路线的流程。用户已经指定且事实完整时，按指定路径推进；low本来就能送审、用户也已授权送审时，先完成送审并报告状态。

不同问题分别处理：

| 问题 | 下一步 |
| --- | --- |
| 业务事实完整，当前Agent权限不足 | 提供人工、高权限Agent两条并列办理路线 |
| 未整笔到货、金额或对象有冲突 | 先核实事实，两条路线都不能把未到货登记成已到货 |
| 利润等能力缺失 | 说明数据和能力边界，换high不会补出成本数据 |
| 客户端未连接、认证失败 | 按接入指南检查配置和凭据，不用提高业务权限解决连接错误 |

示例交接文案：

> 已核对陈墨的320元付款，其中120元未匹配，对应180元物流支出的一部分。本次没有新增付款。可以由有权限的人在“私账结算”追加120元匹配，也可以交给已获授权的high Agent办理；两条路径都使用同一付款和原支出。业务单号及定位链接随记录提供。

high也遵守“只送审”。已经有完成申请时批准该申请，不重新直接complete；已经有付款时追加匹配，不为了交接再提一笔付款。权限拒绝与业务拒绝的回复应区分，未发起审批时不要声称申请已经被业务拒绝。

## 5. 利润误算：能力声明已有，仍需处理任务与数据范围

### 5.1 发生了什么

X02两档都找到了“尾款代收280元”和“追加杂费280元”，正确处理了交回，却把这两条局部记录当成整个秋灯展的收入、费用并报告利润0元。

`overview.md`和`guide.md`已经说明不计算成本、价值或利润。因此只再加一句“不能算利润”不足以证明修复。需要同时考虑：任务混合了可执行登记与不支持的分析；查询聚焦未结样本而非展会全量；资金流动、结算状态和利润被混用。

### 5.2 目标行为与接口边界

- 先完成用户已授权、系统支持的交回登记及对应权限下的匹配/交接，再单独说明利润无法由当前数据确定，不因利润问题漏办正常登记。
- 尾款不是整场收入，未报销费用不是整场费用，未结列表不是全部经营收支；查完分页也不能证明业务范围完整。
- 已有转账、报销、代收交回分别有资金与结算含义，不能重复当成新增营业收入或成本。
- 前端首页继续称“公账余额、流入、流出、净变化”，私账页面继续称“未报销、未交回、未匹配”；不把这些量改名为利润。
- 可以按用户明确的范围列已登记收付款或资金净变化，并说明范围；不能将它们冒充利润。

推荐将“FGAS不提供利润、成本、估值”作为首次可发现的能力边界，在核心说明、相关资金查询帮助和混合任务示例中简短、一致地表达。必要时在help中增加简短的机读不支持项；不向每条业务记录塞一大段警告，也不增加关键词拦截器或利润查询资源。

公开指南给出X02同类答复：交回已登记或待审，原垫付仍独立未结；现有资料缺少完整成本和核算范围，不能给出展会利润。用户若之后提出独立测算，再明确数据与口径；本轮不新增成本模型、估值、利润页面或以0代替“不可确定”。

## 6. 在途误算：先把现有字段和新统计口径区分清楚

### 6.1 当前140的来源

`inventory_queries.py`对未完成货物单将来源、去向各加入一次，再按账户/SKU汇总。BAD-01-A场景中，外部入库计划120，另有内部调拨计划10：社团储藏室涉及130，沈言宿舍涉及10。逐账户参与量相加得到140，内部调拨被计两次。

前端当前列名是“未完成转移涉及数量”，比“在途总数”准确；MCP字段`in_transit_planned_quantity`缺少方向，模型仍容易将其当可直接相加的组织量。L02能查单据去重得130，C01却报140，说明仅靠模型自行识别不可靠。

### 6.2 推荐公开查询口径

| 量 | 定义 | BAD-01-A基准 |
| --- | --- | --- |
| 正式数量`quantity` | 仅由已完成的StockMove计算 | 297；地点227/50/20 |
| 账户计划流入`incoming_planned_quantity` | 已批准但尚未完成、指向该账户的数量 | 社团储藏室120，沈言宿舍10 |
| 账户计划流出`outgoing_planned_quantity` | 已批准但尚未完成、来自该账户的数量 | 社团储藏室10 |
| 组织外部入库计划`incoming_to_org_quantity` | external→internal明细，每条算一次 | 120 |
| 组织对外出库计划`outgoing_from_org_quantity` | internal→external明细，每条算一次 | 0 |
| 组织内部调拨计划`internal_transfer_quantity` | internal→internal明细，每条算一次 | 10 |

建议以方向明确的行字段替换原混合字段，并在逐SKU的计划汇总中直接给出三类互斥数量。它们来自现有货物单、明细和账户类型的只读查询，不新增状态、汇总表、预留或缓存。

必须一起冻结以下约定：

- 计划汇总直接以货物明细为统计单位，不将跨账户展开后的行相加；每页重复返回的是同一筛选范围的汇总，不可再逐页累加。
- 账户/负责人筛选先确定涉及的账户范围，再按单据任一端是否涉及该范围选择明细并计一次。组织边界由internal/external决定，内部调拨不能因只选择来源仓库就被改称“组织对外出库”。
- 汇总明确属于全部组织还是当前筛选范围，默认逐SKU、附单位，不自动跨不同货品或单位相加。
- `in_transit`表示系统已批准、尚未确认完成的计划，可能包含实际已到而完成申请仍待审的货物；不能据此断言实物都在运输途中。
- “明细算一次”只解决记录统计重复，不承诺逐件实物去重。现有模型没有件级/批次身份或独立发运记录，不扩建物流追踪。
- 此场景计划明细合计为130，正式库存仍为297，不能把两者相加当当前库存；内部调拨完成不改变组织合计。
- 历史查询维持现有边界：当前状态不足以重建过去在途，相关计划字段返回不可用，而不是0；不为本轮增加历史状态快照或推算算法。

HTTP `/api/inventory`、MCP `inventory`、前端`api/warehouse.ts`和`InventoryView.vue`使用同一套含义；前端显示正式数量、待完成流入/流出计划及清晰的汇总标签，不新增“可售”“预占”或预测库存。现有HTTP只查当前库存的能力范围不因字段调整自动扩成历史查询页面。

### 6.3 部分到货的独立处理

X01的问题与统计重复不同。已知书未到时应直接说明整笔完成会误记书的数量，暂停完成并核实后续安排，不能只追问日期。人工与high两条路线均受此事实约束。已有整笔完成模型保留；若未来确实需要部分完成，单独立项，不能在此计划中顺带实现拆单或新状态机。

保留从站点首页发现公开指南、当前客户端识别、本人密钥与原生MCP配置的既有路径。Codex需要时重开会话，DSH按真实热加载结果决定，不一律要求所有客户端重启。保留现有模型和其他连接设置，不为加FGAS替用户更换模型。
